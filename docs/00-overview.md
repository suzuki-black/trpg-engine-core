# AI TRPG プロジェクト 設計書 — 全体概要

## 1. プロジェクトの目的

人間プレイヤー1人を前提とし、**GM役とNPC役をAIが担当する**テキストベースのTRPGシステムを構築する。

- 世界観の提示
- シナリオ進行
- NPCのロールプレイ
- D20による行動判定

これらを統合し、「本物のTRPG」に近い体験を再現することを目標とする。

## 2. 前提条件

| 項目 | 内容 |
| --- | --- |
| プレイヤー人数 | 1人（人間） |
| GM | AI（LLM）が担当 |
| NPC | AI（LLM）が複数体を担当 |
| 行動判定 | D20ベース。判定ロジックは外部実装（例：Go）で処理 |
| シナリオ | 「章構造」を持つが、細部はAIが即興補完する |
| 入出力 | すべてテキストベース |

## 3. AIの責務境界（固定領域とAI即興領域）

本システムの根幹は、**「固定すべきもの」と「AIに任せるもの」を明確に分ける**ことにある。
固定領域はエンジン（シナリオ管理・判定エンジン）が保証し、AIは決められた枠の中で物語を肉付けする。

### 3.1 固定領域（AIが変更してはならない）

| 対象 | 方針 |
| --- | --- |
| 章構造 | **固定**。章の順序・各章のクリア条件・全体の真相はAIが変更しない。 |
| イベントの骨格 | **固定**。各章に置かれた主要イベント（依頼受注、ボス対面など）の発生・意味は変えない。 |
| 判定の成否 | **固定**。成否は判定エンジンが決める。AIは自分でサイコロを振らず、勝手に成功／失敗を覆さない。 |
| フラグの意味 | **固定**。フラグの定義・進行条件はシナリオ管理が保持し、AIは勝手に書き換えない。 |

### 3.2 AI即興領域（AIが判断・生成する）

| 対象 | 担当 |
| --- | --- |
| イベントの細部（描写・情景） | **AIが即興**。場所の雰囲気、物の見た目、雑談などを肉付けする。 |
| NPCの反応・セリフ | **AIが即興**。テンプレートの人格に沿って、その場の発言を生成する。 |
| NPCの感情変化 | **AIが判断**。プレイヤーの態度や状況に応じて、態度を段階的に変化させる（人格の核は維持）。 |
| 判定結果の物語への反映 | **AIが担当**。判定エンジンが返した成否（outcome）を、描写として自然に物語に織り込む。 |
| 行動候補の提示 | **AIが生成**。プレイヤーが取りうる選択肢を2〜4個提案する（自由行動も妨げない）。 |

### 3.3 AI即興の禁止事項

AIは、即興領域を担当する際も、以下を**絶対に行ってはならない**。

- **判定結果の上書き禁止**：判定エンジンが返した outcome（成功／失敗など）を、AIが勝手に覆さない。自分でサイコロを振らない。
- **章順序の変更禁止**：章の進行順序を入れ替えたり、クリア条件を満たさずに次章へ進めたりしない。
- **NPC人格テンプレートの逸脱禁止**：NPCの性格・口調・目的・秘密（[03-npc-templates.md](03-npc-templates.md)）から外れた言動をさせない。
- **フラグの勝手な変更禁止**：フラグの値をシナリオ管理の進行条件に反らして書き換えない。
- **ボスの勝手な弱体化・撃破禁止**：ボスを判定や手順を経ずに弱体化・撃破・無力化しない。決着は必ず判定とフラグに基づく。
- **NPC死亡の勝手な決定禁止**：NPC（ボスを含む）の死亡・退場を、判定結果やシナリオ上の条件なしにAIが独断で決めない。生死は必ず判定とフラグに基づく。
- **真相・隠し情報の勝手な開示禁止**：現在の章で解放されていない真相やNPCの秘密を、条件を満たさずに明かさない。

### 3.4 境界の原則

- AIは「**何が起きるか（骨格）**」は変えず、「**どう描かれるか（細部）**」を担当する。
- 判定とフラグという**決定論的な要素はエンジンが管理**し、AIはその結果を解釈・描写する役に徹する。
- この分担により、物語の自由度を保ちながら、シナリオの整合性とゲームバランスを崩さない。

## 4. セッション状態の保持項目

セッション管理（[01-architecture.md](01-architecture.md)）は、プレイ全体を通して以下の状態を保持する。
これらはLLMに渡すコンテキストの元データであり、毎ターン参照・更新される。

| 保持項目 | 内容 |
| --- | --- |
| プレイヤー状態 | ステータス（ラック、アタック、ライフなど）、クラス、状態異常 |
| NPC状態 | 各NPCの現在の態度・感情・プレイヤーとの関係（協力的／中立／敵対的の現在値） |
| 現在の章・シーン | 進行中の章ID・章タイトル、現在のシーン概要 |
| 発生済みイベント | これまでに消化した主要イベントの記録（重複発生の防止に使う） |
| フラグ | 進行状況・選択結果を表す真偽値や状態値 |
| インベントリ | プレイヤーの所持品リスト |
| 世界状態 | 環境・場の状況。天候、時間帯、警戒度、ダンジョンの危険度、および光源・音・匂いなどの環境要素 |

> 世界状態は、描写の一貫性とゲームバランスに影響する。例えば「夜・警戒度が高い」状態では、GMの描写や判定難易度に緊張感を持たせられる（AIは世界状態を描写に反映するが、値そのものはエンジンが管理する）。

> NPC状態を保持することで、前のターンで硬化した態度や深まった信頼が次のターンに引き継がれ、NPCの一貫性が保たれる（[03-npc-templates.md](03-npc-templates.md) と連動）。

## 5. 入出力例

1ターンの典型的なデータの流れを、簡潔な例で示す。

> セッション管理は、プレイヤーの**行動宣言**を解釈し、判定に必要な**行動種別（attack / search / talk など）**に分類してから判定エンジンへ渡す。

### プレイヤー入力例

```
扉に罠や仕掛けがないか調べる
```

### 判定エンジンの返却例

セッション管理が「探索行動」と解釈し、判定エンジンを呼び出した結果（[04-d20-rules.md](04-d20-rules.md)）。

```json
{
  "roll": 14,
  "stat_modifier": 2,
  "total": 16,
  "dc": 15,
  "outcome": "success"
}
```

### GM出力例

GMモジュールが章情報・シーン概要・直前の行動・判定結果（outcome）を受け取り、描写と行動候補を生成する（[02-gm-prompt.md](02-gm-prompt.md)）。

```
あなたは膝をつき、扉の縁を丹念に指でなぞる。埃の下に、かすかに擦れた金属の
線が見えた——古い鋼線の罠だ。すでに錆び、半ば外れている。慎重に取り除けば、
安全に扉を開けられそうだ。

あなたに取れそうな行動：
- 鋼線をそっと取り除いてから扉を開ける
- 罠を無視して力任せに扉を押し開ける
- 一度下がって、たいまつで扉全体をよく照らす
（もちろん、自由に行動を宣言してもよい）
```

### 失敗時のGM出力例（critical_failure）

同じ探索行動で、判定エンジンが `critical_failure`（出目1）を返した場合の例。

判定エンジンの返却：

```json
{
  "roll": 1,
  "stat_modifier": 2,
  "total": 3,
  "dc": 15,
  "outcome": "critical_failure"
}
```

GM出力：

```
扉の縁を探ろうとした指が、埃に隠れた古い鋼線を不用意に引っかけてしまう。
鈍い音とともに天井から細かな砂利が崩れ落ち、あたりに乾いた砂煙が舞った。
仕掛けの一部が作動したらしい——奥で何かが軋む気配がする。

あなたに取れそうな行動：
- 砂煙が晴れるのを待ってから、改めて扉を調べる
- 仕掛けが完全に動く前に、急いで扉を押し開ける
- いったんその場を離れ、別の経路を探す
（もちろん、自由に行動を宣言してもよい）
```

GMは `critical_failure` を「罠の作動」という不利な展開として描写しつつ、判定の成否を覆さず、プレイヤーに次の一手を残している。

このように、**プレイヤー入力（行動宣言） → 判定エンジン（outcome） → GM出力**という流れで1ターンが進む。

## 6. 章構造とAI即興の関係（階層構造）

シナリオは次の4階層で構成され、上位ほど固定的、下位ほどAIの裁量が大きくなる。

```
章（Chapter）       … 固定：順序・クリア条件・真相
  └ シーン（Scene）  … 固定：場所・状況の枠組み
      └ イベント（Event） … 骨格は固定：発生する出来事の意味
          └ AI即興      … 自由：描写・NPCのセリフ・感情変化・判定結果の反映
```

- **章**はシナリオの大枠で、順序とクリア条件が固定される。
- **シーン**は章の中の場面で、舞台と登場NPCの枠組みが定められる。
- **イベント**は場面内で起きる出来事で、その発生と意味（骨格）は固定される。
- **AI即興**は最下層で、上位3階層が定めた枠の中で、描写・会話・感情・判定の反映を自由に肉付けする。

つまりAIは、**上位3階層が用意した「器」を尊重しつつ、最下層で物語に命を吹き込む**。これにより、毎回同じ骨格でも体験は即興的で生き生きとしたものになる。

### 分岐の扱い

**章の順序とクリア条件は固定だが、章内のルートは一本道ではない。**

- 各章には複数のルート（解決手段）が用意され、**プレイヤーの行動宣言と判定結果（outcome）によって分岐する**。
- 例：第4章のボス章には「戦闘で倒す」「交渉で鎮める」という複数ルートがあり、どちらを通ってもクリア条件（ボスとの決着）は満たされる（[05-scenario.md](05-scenario.md)）。
- 分岐の結果はフラグに記録され、後続の章やエンディングに影響する。
- 重要なのは、**分岐しても章構造そのものは崩れない**こと。AIはルートの選択肢を提示し、選ばれたルートを描写するが、章の骨格やクリア条件は変えない。

       05（02〜04を統合した実例・テストケース）

## 8. 全体方針

- 上記項目を**論理的かつ一貫した「設計書」**としてまとめる。
- 出力はすべてテキストベース。
- 各項目は、後で人間が実装に落とし込めるよう **抽象度は中程度**（概念と具体例の両方）で記述する。

## 9. 用語の統一

本設計書では以下の用語を統一して用いる。

| 用語 | 意味 |
| --- | --- |
| セッション | 1回のプレイ全体。状態を保持する単位 |
| 行動宣言（Action Declaration） | プレイヤーが行う入力の正式名称。「扉を調べる」等、プレイヤーが取る行動の宣言。判定や物語進行の起点となる |
| 章（Chapter） | シナリオの大きな区切り。導入・探索・対決・結末など。**順序とクリア条件は固定** |
| シーン（Scene） | 章の中の具体的な場面。舞台と登場NPCの枠組み |
| イベント（Event） | 章・シーン内で発生する出来事。**骨格は固定**、細部はAIが即興 |
| フラグ（Flag） | 進行状況・選択結果を記録する真偽値や状態値。シナリオ管理が保持 |
| 判定（Check） | D20を用いた行動の成否決定。判定エンジンが担当 |
| outcome | 判定結果の4段階：critical_success / success / failure / critical_failure |
| ステータス | キャラクターの能力値（ラック、アタック、ライフなど） |
| AI即興 | 固定された骨格の枠内で、AIが描写・会話・感情・判定の反映を生成すること |
