# 1. TRPGエンジンのアーキテクチャ案

## 1.1 目的

ローカルLLMを前提としたTRPGエンジンの構成を、**役割分担**と**データ構造**の観点から整理する。
本章では図は用いず、「どのモジュールが何を担当するか」を文章で明確にする。

## 1.2 設計の前提

- 人間プレイヤーは1人。
- GM AIと複数のNPC AIはLLMで実装する。
- D20判定は外部ロジック（例：Goなどの判定エンジン）で実装し、LLMには判定の「結果」だけを渡す。
- シナリオは「章構造」を持つが、細部はAIが即興で補完する。

LLMは**物語生成と演技**に専念し、数値計算や成否判定といった**決定論的な処理は外部ロジック**に任せる、という責務分離が基本思想である。

---

## 1.3 コンポーネント一覧

エンジンは6つの主要コンポーネントで構成する。

### (1) セッション管理（Session Manager）

- プレイ全体を統括する司令塔。
- プレイヤー入力の受付、各モジュールへの処理の振り分け、結果の集約と出力を行う。
- 現在のセッション状態（どの章・どのシーンにいるか、直前の行動、フラグの状態）を保持する。
- 会話ログ（履歴）を管理し、LLMに渡すコンテキストを組み立てる。
- 組み立てるコンテキストの構造は「章情報 ＋ シーン概要 ＋ 直前の行動宣言 ＋ 判定結果（outcome） ＋ 関連する状態（プレイヤー状態・NPC状態・世界状態）」を1まとまりとする。

### (2) プレイヤー状態管理（Player State）

- プレイヤーキャラクターのステータス・インベントリ・状態異常などを管理する。
- 判定エンジンに渡すステータス修正値の元データを提供する。
- 戦闘やイベントの結果（ライフ減少、アイテム取得など）を反映して更新する。

**ステータス更新ルール**（更新は無秩序に行わず、以下の規則に従う）：

- **ライフ減少は判定またはイベントに基づく**：ダメージや消耗は、判定結果（outcome）またはシナリオ上のイベントを根拠とする。GMやAIが任意にライフを増減させない。
- **恒久的ステータス変動はシナリオ管理の許可が必要**：能力値の恒久的な上昇・低下（成長・呪い・祝福など）は、シナリオ管理がイベントとして許可した場合のみ反映する。
- **アイテム取得・消費はセッション管理が確定**：インベントリの増減は、描写上の言及だけでは確定せず、セッション管理が正式にコミットして初めて反映される。

### (3) GMモジュール（GM Module / LLM連携）

- ゲームマスター役のLLM呼び出しを担当する。
- 世界の説明、状況描写、判定結果の物語への反映、NPCの動きの要約を行う。
- セッション管理から渡されたコンテキスト（章情報・シーン概要・直前の行動・判定結果）を受け取り、描写と行動候補を生成する。
- 詳細は [02-gm-prompt.md](02-gm-prompt.md) を参照。

### (4) NPCモジュール（NPC Module / LLM連携）

- 各NPCの人格に基づいた応答生成を担当するLLM呼び出し。
- NPC人格テンプレート（性格・口調・目的・秘密）をシステムプロンプトとして読み込む。
- GMから渡される「状況」「プレイヤー発言」をもとに、性格がブレない応答を生成する。
- 詳細は [03-npc-templates.md](03-npc-templates.md) を参照。

**呼び出しタイミングと責務範囲**：

- **GMがNPC発言を必要と判断したときに呼ぶ**：NPCモジュールは常時起動せず、会話シーンなどGMがNPCの発言を要すると判断した場合にのみ呼び出される。
- **NPCはセリフのみ返し、物語進行はGMが統合する**：NPCモジュールが返すのはそのNPCの発言・態度のみ。場面の描写や進行への反映はGMモジュールが受け取って統合する。
- **NPCは単独で物語を進めない**：NPCモジュールはフラグ更新・判定要求・章進行などの進行制御を行わない。あくまで演技（セリフ生成）に専念する。
- **返却形式はセリフ＋トーンのみ**：NPCモジュールが返すのは「発言テキスト」と「トーン（感情・態度の指定。例：冷静／苛立ち／友好的）」だけで、地の文や進行情報は含めない。

### (5) 判定エンジン（D20 Resolver）

- 外部ロジック（例：Go）として実装する決定論的モジュール。
- 行動種別・使用ステータス・難易度クラスを受け取り、D20の出目＋ステータス修正値で成否を計算する。
- クリティカル成功／クリティカル失敗を判定する。
- LLMには結果（成功／失敗／クリティカルなど）のみを返す。
- 詳細は [04-d20-rules.md](04-d20-rules.md) を参照。

### (6) シナリオ管理（Scenario Manager）

- 章・イベント・フラグの状態を管理する。
- 現在の章とクリア条件を保持し、フラグの達成状況に応じて章を進行させる。
- 現在の章・イベント・フラグに応じて、GMの振る舞いに制約を与える。
- 詳細なシナリオデータは [05-scenario.md](05-scenario.md) を参照。

**シナリオ管理が課す制約の種類**（GMやNPCの振る舞いを次の点で縛る）：

- **未解放情報の禁止**：現在の章で解放されていない真相・伏線・場所の情報を出させない。
- **未登場NPCの情報禁止**：まだ登場していないNPCの存在・名前・事情を漏らさせない。
- **ボスの弱体化・撃破禁止**：判定や手順を経ないボスの弱体化・撃破・無力化を許可しない。
- **章クリア条件未達での進行禁止**：現在の章のクリア条件を満たさないまま次章へ進めさせない。
- **NPC死亡の独断決定の禁止**：判定結果やイベント条件のないNPC（ボス含む）の死亡・退場を許可しない。

## 1.4 コンポーネント間の関係

処理の流れは、セッション管理を中心としたハブ＆スポーク型で整理する。

### 基本フロー（1ターンの流れ）

1. **プレイヤー入力 → セッション管理**
   プレイヤーが行動（例：「扉を調べる」）をテキストで入力する。セッション管理が受け取る。

2. **セッション管理 → シナリオ管理（制約の確認）**
   現在の章・イベント・フラグを参照し、その行動が判定を要するか、どんな制約があるかを確認する。

3. **セッション管理 → 判定エンジン（必要な場合）**
   行動が判定を要する場合、行動種別・使用ステータス・難易度クラスを判定エンジンに渡す。判定エンジンは成否（成功／失敗／クリティカル）を返す。

4. **セッション管理 → GMモジュール（物語生成）**
   GMモジュールに、章情報・シーン概要・直前の行動・判定結果を渡す。GMは状況描写と行動候補を生成する。

5. **必要に応じて NPCモジュール**
   会話シーンや、GMがNPCの発言を要する場合、NPCモジュールがプレイヤー発言・状況に応じた応答を生成する。

6. **セッション管理 → プレイヤーへ出力**
   GM描写（＋NPC発言）を統合してプレイヤーに提示する。フラグやプレイヤー状態の更新があれば反映する。

### 関係のまとめ

- **プレイヤー入力 → セッション管理 → GMモジュール**
- **GMモジュール → 判定エンジン呼び出し → 結果を元に物語生成**
  （実際の呼び出しはセッション管理が仲介するが、GMの描写は判定結果に従う）
- **NPCモジュール → プレイヤー発言や状況に応じた応答生成**
- **シナリオ管理 → 現在の章・イベント・フラグに応じてGMの振る舞いを制約**

## 1.5 データ構造の概要

実装言語に依存しない概念モデルとして、主要なデータ構造を示す。

### (A) プレイヤーキャラクター（PlayerCharacter）

| フィールド | 内容 | 例 |
| --- | --- | --- |
| name | 名前 | "アルド" |
| class | クラス | 戦士、盗賊、僧侶 など |
| stats | ステータス群 | luck（ラック）, attack（アタック）, life（ライフ）など |
| inventory | 所持品リスト | ["たいまつ", "ロープ", "回復薬"] |
| flags | キャラ固有の状態 | 状態異常・称号など（任意） |

ステータスは「能力修正値の算出元」として使う。例：attack が高いほど攻撃判定に有利な修正がかかる。

### (B) シナリオ（Scenario / Chapter）

| フィールド | 内容 | 例 |
| --- | --- | --- |
| chapter_id | 章ID | "ch01" |
| title | 章タイトル | "村での依頼" |
| events | 主要イベント一覧 | 依頼受注、情報屋との会話 など |
| clear_condition | クリア条件 | "依頼を受諾し遺跡の場所を聞く" |
| flags | 章に関わるフラグ | quest_accepted: bool など |

### (C) 判定リクエスト（CheckRequest）

| フィールド | 内容 | 例 |
| --- | --- | --- |
| action_type | 行動種別 | attack, search, talk など |
| used_stat | 使用ステータス | attack, luck, life など |
| difficulty_class | 難易度クラス（ランクまたは数値） | easy / normal / hard / very_hard |

判定エンジンはこのリクエストを受け取り、D20の出目と used_stat の修正値を合算し、difficulty_class（DC）と比較して成否を返す。

---

## 1.6 判定リクエストの入力決定プロセス

判定リクエスト（CheckRequest）の各項目は、**単一のモジュールがまとめて決めるのではなく、責務に応じて分担して決定**される。これにより、判定の客観性とバランスが保たれる。

| リクエスト項目 | 決定するモジュール | 決定内容 |
| --- | --- | --- |
| action_type（行動種別） | **セッション管理** | プレイヤーの行動宣言を解釈し、attack / search / talk などに分類する。 |
| difficulty_class（難易度クラス） | **シナリオ管理** | 現在の章・イベント・状況に応じて、easy〜very_hard（またはDC数値）を決定する。 |
| used_stat / ステータス修正値 | **プレイヤー状態管理** | 行動種別に対応する使用ステータスを特定し、その修正値を提供する。 |

決定プロセスの流れ：

1. **セッション管理**がプレイヤーの行動宣言を受け取り、`action_type` に分類する。
2. **シナリオ管理**が現在の状況を踏まえて `difficulty_class` を決定する。
3. **プレイヤー状態管理**が `used_stat` とその修正値を提供する。
4. セッション管理がこれらを1つの判定リクエストに統合し、**判定エンジン**へ渡す。
5. 判定エンジンが outcome を返し、GMモジュールが物語に反映する。

> このように、行動の「分類」「難易度」「能力値」を別々のモジュールが受け持つことで、AI（GM）が自分に有利・不利な判定を恣意的に作ることを防ぐ。

---

## 1.7 責務分担の要約

| 関心事 | 担当 |
| --- | --- |
| 進行管理・状態保持・コンテキスト組み立て | セッション管理 |
| キャラクター数値・所持品 | プレイヤー状態管理 |
| 物語・描写・行動候補 | GMモジュール（LLM） |
| NPCの演技・会話 | NPCモジュール（LLM） |
| 成否計算・乱数・クリティカル判定 | 判定エンジン（外部ロジック） |
| 章進行・イベント・フラグ・制約 | シナリオ管理 |

この分離により、「LLMは創造を、外部ロジックは決定論を」担当する構成となり、再現性とゲームバランスの調整がしやすくなる。
